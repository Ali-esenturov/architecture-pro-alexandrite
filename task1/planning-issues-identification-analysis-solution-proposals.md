# 1. Существующие и потенциальные проблемные места

## 1.1. Архитектура и производительность

- **Расчёт стоимости изделия — тяжёлая и длительная операция**
  - Выполняется в MES
  - Длительность: от 2–3 до 30 минут
  - Используется как внутренними, так и внешними клиентами через API

- **Отсутствие горизонтального масштабирования сервисов**
  - Каждый сервис запущен в одном инстансе
  - Рост нагрузки линейный, масштабирование отсутствует

- **Синхронная зависимость бизнес-процессов от MES**
  - MES является узким местом всего бизнес-процесса
  - При деградации MES замедляется вся цепочка обработки заказов

- **Единичные инстансы баз данных (read/write)**
  - Нет read-replica
  - Нет разделения OLTP и read-нагрузки

- **Медленная загрузка дашборда операторов**
  - Дашборд строится на основе прямых запросов к MES DB
  - Используются фильтры и сортировки по большому объёму данных
  - Нет кеширования и подготовленных read-моделей

## 1.2. Интеграция и обмен данными

- **Слабая изоляция асинхронных процессов**
  - RabbitMQ используется, но:
    - нет чётко описанных контрактов событий
    - нет DLQ и мониторинга очередей

- **Статусы заказа изменяются в разных системах**
  - CRM, MES и онлайн-магазин меняют статусы независимо
  - Нет централизованного контроля жизненного цикла заказа

## 1.3. Наблюдаемость (Logging, Tracing, Monitoring)

- **Отсутствие распределённого трейсинга**
  - Невозможно отследить путь заказа между системами

- **Недостаточное логирование бизнес-событий**
  - Логи не структурированы
  - Нет корреляции по orderId

- **Отсутствие метрик бизнес-процессов**
  - Нет измерения времени расчёта цены
  - Нет SLA по статусам
  - Нет мониторинга очередей

## 1.4. Процессы разработки и поставки

- **Ручное E2E-тестирование как блокирующий этап**
  - Один QA-инженер
  - Отсутствие автоматизации
  - Частые задержки релизов

# 2. Инициативы по устранению проблем

## 2.1. Архитектурные инициативы

- Перевести расчёт стоимости изделия в асинхронный процесс (job-based)
- Разделить API расчёта и воркеры выполнения расчёта
- Добавить горизонтальное масштабирование MES
- Ограничить входящую нагрузку на API (rate limit / concurrency limit)

## 2.2. Производительность и данные

- Внедрить кеширование (Redis) для:
  - дашборда операторов
  - статусов заказов
- Создать отдельную read-модель для дашборда операторов
- Добавить read-replica для MES DB
- Оптимизировать SQL-запросы и индексацию

## 2.3. Наблюдаемость

- Внедрить distributed tracing (OpenTelemetry)
- Ввести структурированное логирование с orderId, traceId
- Добавить метрики бизнес-процессов и очередей
- Настроить алерты по SLA и деградациям

## 2.4. Процессы разработки

- Автоматизировать E2E smoke-тесты
- Внедрить безопасные схемы деплоя (canary / blue-green)

# 3. Приоритизация инициатив и ход рассуждений

**Критерии приоритизации:**  

- Влияние на бизнес (задержки заказов, жалобы)
- Устранение узких мест
- Снижение операционных рисков
- Подготовка фундамента для масштабирования

**Приоритет 1 — критический**  

- Асинхронный расчёт стоимости изделия
  - Устраняет главный bottleneck
  - Позволяет масштабировать расчёты независимо
  - Снижает задержки для всех клиентов

- Кеширование и read-модель дашборда операторов
  - Прямо улучшает UX операторов
  - Снижает нагрузку на БД
  - Быстро реализуется

- Наблюдаемость (tracing, логирование, метрики)
  - Делает систему управляемой
  - Позволяет измерять эффект оптимизаций

**Приоритет 2 — масштабируемость**  

- Горизонтальное масштабирование сервисов
- Read-replica для БД
- Rate limiting для внешнего API

**Приоритет 3 — процессы**  

- Автоматизация E2E
- Улучшение CI/CD

# 4. Целевая архитектура через 6 месяцев

**Характеристики целевой архитектуры:**  

- Асинхронная, event-driven
- Горизонтально масштабируемая
- Разделение write и read нагрузки
- Полная наблюдаемость бизнес-процессов

**Ключевые изменения:**  

- MES API принимает запрос и ставит задачу в очередь
- Отдельные воркеры считают стоимость
- Результаты публикуются как события
- Дашборды работают через кешированные read-модели
- Все запросы и события трассируются

# 5. Если можно реализовать только 3 инициативы

**Выбор:**  

- Асинхронный расчёт стоимости
- Кеширование и read-модель дашборда операторов
- Distributed tracing и метрики

**Обоснование:**  

- Эти инициативы устраняют основные текущие боли
- Дают измеримый эффект для бизнеса
- Создают основу для дальнейшего масштабирования и оптимизации
