# Логирование системы

## 1. Системы, из которых требуется сбор логов

Логирование необходимо включить во всех компонентах, которые:
- участвуют в жизненном цикле заказа
- изменяют состояние заказа
- выполняют длительные или критичные операции

### Системы для сбора логов

- Онлайн-магазин (Spring Boot)
- CRM (Spring Boot)
- MES API (C# backend)
- MES calculation workers

---

## 2. Логи уровня INFO (основные бизнес- и системные события)

Уровень **INFO** используется для фиксации ключевых событий, происходящих в штатном режиме, и необходимых для аудита и анализа бизнес-процессов.

| Событие | Система | Что логируем | Зачем |
|-------|---------|--------------|-------|
| Создание заказа | Онлайн-магазин | timestamp, order_id, customer_id | Фиксация начала жизненного цикла заказа |
| Загрузка 3D-модели | Онлайн-магазин | timestamp, order_id, model_size | Анализ проблем загрузки файлов |
| Отправка заказа | Онлайн-магазин | timestamp, order_id | Подтверждение перехода в SUBMITTED |
| Публикация сообщения | CRM | timestamp, order_id, queue_name | Контроль передачи заказа в MES |
| Начало расчёта стоимости | MES worker | timestamp, order_id, complexity | Анализ начала тяжёлых операций |
| Завершение расчёта стоимости | MES worker | timestamp, order_id, duration | Контроль времени расчёта |
| Изменение статуса заказа | CRM / MES | timestamp, order_id, old_status, new_status | Аудит бизнес-процесса |
| Начало производства | MES | timestamp, order_id, operator_id | Контроль ручных этапов |
| Завершение производства | MES | timestamp, order_id | Анализ сроков изготовления |
| Отправка заказа | MES | timestamp, order_id, shipment_id | Контроль логистики |
| Закрытие заказа | CRM | timestamp, order_id | Завершение жизненного цикла заказа |

---

## 3. Использование других уровней логирования

### DEBUG
Используется временно и ограниченно:
- детальные шаги расчёта стоимости
- промежуточные вычисления
В production отключён по умолчанию.

---

### WARN
Используется при:
- превышении ожидаемого времени операций
- повторных ретраях
- деградациях без полной недоступности сервиса

Примеры:
- расчёт стоимости превышает SLA
- повторная обработка сообщения из очереди

---

### ERROR
Используется при:
- ошибках расчёта стоимости
- потере сообщений
- неконсистентных статусах заказа

---

### FATAL / CRITICAL
Используется при:
- невозможности продолжать работу сервиса
- аварийном завершении приложения

---

## 4. Мотивация внедрения логирования

Логирование необходимо компании Alexandrite для перехода от реактивного реагирования на инциденты к управляемой и предсказуемой эксплуатации системы.

### Что даёт логирование компании

- аудит и восстановление полной истории заказа
- ускорение расследования инцидентов и снижение MTTR
- выявление узких мест при росте нагрузки
- повышение качества ответов службы поддержки клиентам

---

## 5. Метрики, на которые влияет внедрение логирования

| Метрика | Влияние логирования |
|-------|---------------------|
| MTTR | Сокращается за счёт быстрого RCA |
| Количество жалоб | Снижается за счёт оперативного реагирования |
| SLA по заказам | Улучшается за счёт прозрачности этапов |
| Потерянные заказы | Снижается благодаря аудиту событий |
| Производительность операторов | Повышается за счёт анализа задержек |

## 6. Приоритизация внедрения логирования и трейсинга

Команда не сможет реализовать логирование и трейсинг во всех системах одновременно, поэтому приоритизация строится по критериям:
- **бизнес-критичность** (влияние на выручку, партнёров, клиентов)
- **операционная критичность** (работа операторов и обработка заказов)
- **вероятность быть узким местом** (latency/ошибки/зависания)

### Приоритет 1 — критические системы (внедрять в первую очередь)

1. **MES API**
   - Через него создаются заказы партнёров (B2B), поэтому любые деградации напрямую влияют на партнёрский канал и потенциальную выручку
   - MES API участвует в выдаче списка заказов операторам; именно здесь часто проявляются проблемы производительности (медленные запросы, фильтры, пагинация, N+1)
   - Логи и трейсы MES API позволяют быстро разделить причины деградации: API/БД/очередь/сетевые задержки

2. **MES calculation workers**
   - Основной вычислительный bottleneck (2–30 минут на расчёт)
   - Источник задержек жизненного цикла заказа на этапе `PRICE_CALCULATED` и потенциальных ошибок обработки 3D-моделей
   - Трейсы и логи здесь критичны для контроля SLA и диагностики “зависаний” расчёта

3. **CRM**
   - Центральная система управления статусами заказа и подтверждениями (`MANUFACTURING_APPROVED`, `CLOSED`)
   - Без логов и трейсинга CRM сложно расследовать инциденты консистентности статусов между CRM и MES

### Приоритет 2 — входной поток заказов

4. **Онлайн-магазин**
   - Точка входа B2C заказов: влияет на клиентский опыт и конверсию
   - Нужен трейсинг/логирование для контроля стабильности оформления заказа, загрузки 3D-моделей и переходов статусов `INITIATED - FILE_UPLOADED - SUBMITTED`

### Приоритет 3 — инфраструктура и данные

5. **RabbitMQ**
   - Логи и метрики очередей важны для диагностики зависаний асинхронных этапов (рост очереди, DLQ, ретраи)
   - Однако при отсутствии инструментирования сервисов трассировка будет неполной, поэтому RabbitMQ логично подключать после ключевых сервисов

6. **Базы данных**
   - Slow query logs и мониторинг соединений помогают выявлять корневые причины деградации дашбордов и API
   - Подключаются после того, как появится базовая наблюдаемость на уровне сервисов, чтобы связывать симптомы в БД с конкретными запросами/эндпоинтами


# Предлагаемое решение

## Технологии и компоненты
- **Структурированные JSON-логи** во всех backend-сервисах: **Shop API**, **CRM API**, **MES API** и **MES workers**
- **Log collector:** Fluent Bit (или Vector) на каждом инстансе (EC2)
- **Log storage:** OpenSearch (или Elasticsearch)
- **UI:** OpenSearch Dashboards (или Kibana)
- **Alerting/Anomaly:** OpenSearch Alerting (правила + пороги; при необходимости — простая аномалистика)

## Минимальные доработки в сервисах
- Писать логи **только в JSON**
- Единые поля (минимум):
  - `timestamp`, `level`, `service`, `env`
  - `order_id`, `partner_id` (B2B), `operator_id` (операторы)
  - `endpoint`, `http_status`, `duration_ms`
  - `trace_id` (если трейсинг уже внедрён)
  - `error_type`, `error_message` (для WARN/ERROR)
- В prod: **DEBUG выключен** по умолчанию (включается точечно на ограниченное время)

# Политика безопасности логов

## Работа с чувствительными данными
- **Запрещено логировать:** email/phone/address/payment, токены/секреты, содержимое 3D-файлов, URL с временными токенами
- Если часть данных нужна для поддержки — только **маскирование** (например, частично скрытый email/телефон)

## Доступ к логам (внутренний/внешний)
- UI логов доступен **только из внутренней сети/VPN**
- **SSO + RBAC**:
  - `Support`: поиск по `order_id`, чтение INFO/WARN
  - `Engineering`: доступ к ERROR и расширенным полям
  - `SRE/Admin`: управление индексами/ретеншном/алертами
- Шифрование каналов: **TLS** collector - storage и UI - storage

---

# Политика хранения логов (retention/индексы/размер)

## Индексация
- Минимум: индексы по окружениям `prod-*`, `release-*`, `dev-*`
- Опционально: доп. разделение по системам (например, `prod-mes-api-*`, `prod-crm-api-*`) если нужен разный доступ/ретеншн

## Retention (пример)
- **prod:** 30 дней  
- **release/test:** 14 дней  
- **dev:** 7 дней

## Контроль объёма
- Не писать в INFO высокочастотный «шум» (health-check и т.п.)
- DEBUG не хранить в prod
- Часть повторяющихся событий переводить в метрики (счётчики/гистограммы), чтобы не раздувать логи

# Из системы сбора в систему анализа: алерты и аномалии

## Алертинг (нужен)
Примеры алертов:
- всплеск **ERROR** по `MES API` / `CRM API` / `Shop API`
- рост **WARN timeout** (DB, очередь, публикация сообщений)
- **нет событий** `order_created` (B2B/B2C) в течение N минут (возможный outage входного канала)
- есть `SUBMITTED`, но долго нет `PRICE_CALCULATED` (зависание процесса)

## Поиск аномалий (нужен базовый)
- резкий рост `order_created` / `file_uploaded` / `B2B order created` (возможный DDoS/боты/ошибка интеграции)
- резкий рост 4xx/401/403 (сканирование/атаки/неверные ключи партнёров)
- всплеск ошибок валидации/парсинга 3D-моделей
