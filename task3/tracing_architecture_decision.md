# Системы и точки, которые необходимо покрыть трейсингом
Трейсинг должен покрывать весь жизненный цикл заказа, так как заказ проходит через несколько систем и асинхронных этапов, где возможны задержки и сбои.

## Системы, подлежащие покрытию трейсингом
- Онлайн-магазин (Vue + Spring Boot)
- CRM (Vue + Spring Boot)
- MES API (React + C# backend)
- MES calculation workers
- RabbitMQ
- Базы данных
- Redis

## Критические точки, где заказ может «сломаться» или зависнуть
### Отправка заказа из онлайн-магазина
- Потеря запроса
- Ошибка валидации
- Некорректный переход в статус SUBMITTED
### Публикация сообщения в RabbitMQ
- Сообщение не попало в очередь
- Сообщение опубликовано без подтверждения
- Потеря correlation данных
### Ожидание обработки в очереди
- Очередь переполнена
- Сообщение долго не обрабатывается
- Нарушение SLA ожидания
### Расчёт стоимости в MES
- Длительное выполнение
- Ошибка обработки 3D-модели
- Повторные ретраи без явной причины
### Обновление статуса заказа
- Несогласованность статусов между CRM и MES
- Событие обработано частично
- Потеря события
### Ручные этапы (операторы)
- Заказ долго находится в статусе MANUFACTURING_STARTED
- Нет понимания, техническая или операционная причина задержки

## Данные которые должны попадать в трейсинг
Для обеспечения end-to-end наблюдаемости каждый trace должен содержать как технический, так и бизнес-контекст.

### Обязательные данные для трейсинга

| Данные | Зачем нужны |
|------|-------------|
| trace_id | Связывает все операции одного заказа |
| span_id | Идентифицирует отдельные этапы обработки |
| order_id | Связь с конкретным заказом |
| order_status | Понимание текущего этапа процесса |
| service_name | Определение системы-источника задержки |
| operation_name | Понимание выполняемого действия |
| timestamp_start / end | Расчёт latency |
| duration | Поиск узких мест |
| error_flag | Быстрое обнаружение сбоев |
| error_message | Диагностика причины ошибки |

### Дополнительные (необязательные) данные

| Данные | Зачем нужны |
|------|-------------|
| complexity | Анализ влияния сложности изделия на сроки |
| queue_name | Диагностика проблем очередей |
| retry_count | Выявление нестабильных операций |
| worker_id | Поиск проблемных воркеров |
| client_type | Разделение пользовательских и операторских сценариев |


## Мотивация внедрения трейсинга

В текущей системе компании Alexandrite заказ проходит через несколько сервисов и асинхронных этапов. При росте нагрузки и увеличении времени расчёта стоимости становится невозможно быстро определить, где именно возникает задержка или сбой.

Без трейсинга:
- диагностика инцидентов занимает много времени
- причины проблем выявляются реактивно
- технические и бизнес-команды опираются на предположения, а не на данные

### Что даст трейсинг компании

Технические эффекты:
- Сокращение MTTR. Быстрая локализация проблемного сервиса или этапа
- Прозрачность асинхронных процессов. Видно реальное время ожидания в очередях и воркерах
- Упрощение отладки сложных инцидентов. Один trace вместо анализа логов из разных систем

Бизнес-эффекты:
- Контроль SLA по расчёту стоимости. Возможность доказуемо измерять выполнение обязательств
- Снижение количества жалоб. Проблемы устраняются до того, как становятся массовыми

### Метрики, на которые повлияет внедрение трейсинга

| Метрика | Как трейсинг влияет |
|-------|---------------------|
| End-to-end order latency | Позволяет измерять полный путь заказа |
| Price calculation duration | Даёт точное распределение времени расчёта |
| Queue wait time | Видно фактическое ожидание в очереди |
| Error rate по этапам | Позволяет локализовать источник ошибок |
| MTTR | Существенно сокращается за счёт прозрачности |


## Предлагаемое решение

### Общий подход
Для реализации distributed tracing в системе Alexandrite предлагается внедрить OpenTelemetry как единый стандарт сбора трейсов во всех сервисах с последующей отправкой данных в централизованное хранилище и UI для анализа.

### Ключевая идея
Каждый заказ получает единый trace_id, который проходит через:
- онлайн-магазин
- CRM
- RabbitMQ
- MES API
- MES calculation workers
- базы данных и кеш

Это обеспечивает end-to-end наблюдаемость жизненного цикла заказа, включая асинхронные этапы.

### Необходимые технологии и шаги
Инструментирование сервисов
- OpenTelemetry SDK
- Spring Boot (онлайн-магазин, CRM)
- C# backend (MES API, calculation workers)

Функции:
- автоматическое создание span-ов для HTTP-запросов
- ручные span-ы для бизнес-операций (смена статуса, расчёт стоимости)
- генерация и распространение trace_id

### Backend Трейсинга

OpenTelemetry Collector
- принимает трассы от сервисов
- фильтрует, агрегирует, семплирует
Jaeger / Grafana Tempo
- хранение и визуализация трейсов

## Компромиссы и ограничения
Внедрение трейсинга не является бесплатным и универсальным решением. Ниже перечислены осознанные компромиссы.

### Стоимость внедрения и поддержки
Требуется:
- инструментирование кода
- обучение команды
- поддержка инфраструктуры трейсинга

Точка компромисса: на первом этапе трейсинг может быть включён только для ключевых флоу (расчёт стоимости, смена статусов).

### Ручные этапы производства
- Долгое нахождение заказа в статусе MANUFACTURING_STARTED не всегда связано с технической проблемой
- Трейсинг фиксирует факт ожидания, но не причину (человеческий фактор)

Точка компромисса: трейсинг фиксирует только факт входа/выхода из статуса. Причины задержек анализируются дополнительно бизнес-метриками

### Стоимость хранения
- Атрибуты вроде order_id увеличивают объём данных
- Возможна нагрузка на storage

Точка компромисса: требуется sampling и TTL


## Аспекты безопасности

### Ограничение доступа к системе трейсинга
Доступ к UI трейсинга:
- только через внутреннюю сеть / VPN
- только для сотрудников компании

### Аутентификация и авторизация
- Интеграция с корпоративной системой аутентификации (SSO)
- Ролевая модель: Support - просмотр трейсов, Engineer - расширенный доступ, Admin - управление системой

### Защита чувствительных данных
Запрет на передачу:
- персональных данных клиентов
- содержимого 3D-моделей
В трейсах используются:
- идентификаторы
- технические и агрегированные данные

### Сетевые меры безопасности
- TLS для передачи трасс
- Ограничение доступа к OpenTelemetry Collector
- Отдельные service accounts для сервисов
